# Каскад (split-path): пп. 2.4 и 2.5 ревью

**Статус: отложено.** В v1 каскада нет ([scope.md](scope.md)). Ниже — предложение на v2, чтобы решения v1 ему не мешали. Кода по нему нет.

## Склейка двух соединений (2.4)

- Клиент аутентифицируется на каждом сервере отдельно, учётные данные привязаны к экспортёру своего соединения ([credentials.md](credentials.md)) — так уже в v1.
- В учётные данные добавляется роль соединения (`uplink`/`downlink`) внутри подписанных данных: подпись одного направления не проходит на другом.
- Половины сессии склеиваются не по `session_id` (он несекретный), а по `join_tag = HMAC(secret, "ASTP-M join v1" ‖ session_nonce ‖ binding_up ‖ binding_down)`. `session_nonce` выдаёт сервер A в `CONFIG` (TLV `0x000C`), `binding_*` — экспортёры обоих соединений; клиент предъявляет `join_tag` серверу B (TLV `0x000D`).
- Серверы A и B обмениваются состоянием сессии по своему каналу (mTLS между узлами); падение одной половины закрывает обе.

## Путь ответа управляющих кадров (2.5)

Рекомендация — тонкий обратный канал на каждом соединении:

- `PONG`, `WINDOW`, `CONFIG_ACK` идут по тому же соединению, что и запрос, — существующие кадры работают без изменений;
- только кадры `TUN_*` однонаправлены (аплоад по одному соединению, даунлоад по другому);
- `keepalive`/`idle_timeout` действуют на каждое соединение отдельно.

Если обратного канала не будет, под кадры с идентификатором пути занимаются зарезервированные типы `0x40..=0x4F`.

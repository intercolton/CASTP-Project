# Сессия ASTP-M v1

**Статус: предложение.** Код: `astp-session` (состояние и обмен кадрами), `astp-transport` (HTTP-обёртка).

## Почему внутри HTTP

Публичный ALPN — `h2` (TCP) и `h3` (QUIC). Сервер на 443 должен для любого постороннего выглядеть как обычный HTTPS-сайт, включая активное зондирование. Поэтому сессия — это один HTTP-запрос с потоковыми телами в обе стороны:

- тело запроса — кадры клиент → сервер;
- тело ответа — кадры сервер → клиент.

HTTP/2 и HTTP/3 дают полнодуплексные потоки, свой контроль потока и мультиплексирование; ничего похожего на «голый» протокол поверх TLS на проводе нет.

## Установка

1. TLS 1.3 (TCP, ALPN `h2`) или QUIC v1 (ALPN `h3`). Сертификат — обычный публичный; проверка у клиента всегда включена.
2. Клиент вычисляет привязку к каналу: экспортёр TLS `EXPORTER-ASTP-M auth v1`, 32 байта, пустой контекст (`astp-crypto::channel_binding`; для QUIC — `quinn::Connection::export_keying_material` с тем же label).
3. Клиент отправляет запрос:
   - `POST {session_path}` — путь задаётся в конфигурации сервера и клиента (секретный, по умолчанию генерируется при установке; фиксированный путь в коде был бы отпечатком);
   - `authorization: Bearer <base64url без '='(credential)>` — см. [credentials.md](credentials.md);
   - `content-type: application/octet-stream`.
4. Сервер проверяет метод, путь и учётные данные. **Любая** неудача (не тот путь, не тот метод, нет заголовка, неверная подпись, неизвестный клиент) даёт один и тот же ответ «сайта-прикрытия»: `404` с тем же телом и заголовками, что и для любого неизвестного пути. Тело запроса читается и отбрасывается до лимита. Проверка подписи выполняется всегда, в том числе для неизвестного ключа, чтобы время ответа не различалось.
5. Успех: `200`, `content-type: application/octet-stream`, тело ответа остаётся открытым.
6. Первый кадр сервера — `CONFIG`. Клиент отвечает `CONFIG_ACK` с тем же `cfg_id` и кодом `0` (принято) или ненулевым (отказ, после чего клиент шлёт `DISCONNECT`). Пока `CONFIG_ACK 0` не получен, сервер не пересылает клиенту пакеты туннеля, а клиент не шлёт их серверу.

## Кадры в сессии

| Кадр | Кто шлёт | Правило v1 |
|---|---|---|
| `CONFIG` | сервер | Первый кадр сервера. Повторный `CONFIG` с новым `cfg_id` допускается (смена параметров), клиент снова отвечает `CONFIG_ACK` |
| `CONFIG_ACK` | клиент | На каждый `CONFIG` |
| `ROUTE_UPDATE` | сервер | Добавочные маршруты, без подтверждения |
| `TUN_IPV4` / `TUN_IPV6` | оба | Один IP-пакет. Сервер проверяет, что адрес источника — выданный клиенту, иначе пакет отбрасывается |
| `PING` / `PONG` | оба | `PONG` возвращает те же 8 байт по тому же соединению |
| `WINDOW` | оба | Кредит на байты пакетов туннеля (ниже) |
| `DISCONNECT` | оба | Код и причина, затем закрытие потока |
| `PADDING` | оба | Игнорируется |

Каждый кадр кодируется с профилем маскировки v1 (`encode_camouflage`).

Неизвестный тип кадра, флаг `KEY_EPOCH`, кадр не своей стороны (например, `CONFIG` от клиента), `TUN_*` до подтверждения конфигурации, превышение кредита — ошибка протокола: `DISCONNECT` с кодом `1` и закрытие.

## Поток данных и `WINDOW`

HTTP/2 и QUIC уже ограничивают поток байт, но не отличают пакеты туннеля от служебных кадров. `WINDOW` даёт отправителю правило, что делать при перегрузке:

- Каждая сторона начинает с кредитом `INITIAL_WINDOW = 1 MiB` на суммарный размер тел `TUN_*`, полученных от неё другой стороной.
- Получатель, обработав пакеты (записав их в TUN), возвращает кредит кадром `WINDOW(n)`, как только набралось `n ≥ INITIAL_WINDOW / 2`.
- Отправитель без кредита **отбрасывает** пакет (как переполненная очередь интерфейса) и считает потери. Пакеты туннеля не ждут: TCP внутри туннеля сам снизит скорость по потерям, а ожидание держало бы задержку.
- Пакет сверх выданного кредита — ошибка протокола.

## Живость

- TLV `keepalive` (мс) и `idle_timeout` (мс) приходят в `CONFIG`. По умолчанию 25 000 и 90 000.
- Если `keepalive` мс ничего не отправлялось, сторона шлёт `PING` со случайными 8 байтами.
- Если `idle_timeout` мс ничего не принято, сторона шлёт `DISCONNECT` с кодом `2` и закрывается.

## Коды `DISCONNECT`

| Код | Значение |
|---|---|
| 0 | обычное завершение |
| 1 | ошибка протокола |
| 2 | простой дольше `idle_timeout` |
| 3 | клиент отверг конфигурацию |
| 4 | сервер останавливается |
| 5 | сессию этого клиента вытеснила новая |

`CONFIG_ACK` с кодом, отличным от 0, означает отказ; значения кода v1 не различает.

## Одна сессия на клиента

Новая успешная сессия того же клиента вытесняет старую (`DISCONNECT 5`): у клиента один адрес туннеля, и две сессии делили бы его.

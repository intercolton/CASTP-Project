# Учётные данные v1

**Статус: предложение.** Код: `astp-crypto::KeyTable` (сервер), `astp-crypto::client_credential` (клиент). `StaticTokenAuthenticator` остаётся тестовым.

## Ключ клиента

- Каждому клиенту выдаётся секрет — 32 случайных байта. В конфигурации он записан как base64url без `=`.
- Идентификатор ключа выводится из секрета: `key_id = SHA-256("ASTP-M key id v1" ‖ secret)[0..16]`. Отдельно хранить его не нужно, по нему сервер находит секрет. По `key_id` секрет не восстановить.
- На сервере — список клиентов `[[clients]]` с именем, секретом и выданными адресами туннеля. Отзыв — удаление записи и перезапуск (или перечитывание конфигурации).

## Учётные данные одного соединения

```
credential = 0x01 ‖ key_id (16) ‖ HMAC-SHA256(secret, "ASTP-M credential v1" ‖ channel_binding) (32)
```

49 байт, в заголовке `authorization: Bearer <base64url>`.

- `channel_binding` — экспортёр TLS этого соединения. Учётные данные, перехваченные или выданные для одного соединения, на другом не проходят (другой экспортёр).
- Метка версии в начале позволяет сменить формат позже.

## Проверка на сервере

1. Длина 49 и версия `0x01`, иначе — отказ.
2. Поиск секрета по `key_id`. Если ключ не найден, HMAC всё равно вычисляется на фиктивном ключе: время ответа не выдаёт, существует ли ключ.
3. Сравнение тега за постоянное время (`subtle`).
4. Любой отказ для собеседника одинаков (ответ сайта-прикрытия); причина пишется только в журнал сервера.

## Что сознательно не сделано в v1

- Срок действия ключа и ротация без перезапуска.
- Асимметричные ключи клиента (mTLS остаётся опцией `astp-crypto`, но v1 его не включает: клиентский сертификат в рукопожатии виден и отличает соединение от браузерного).

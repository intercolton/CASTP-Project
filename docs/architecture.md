# Архитектура

Документ фиксирует устройство репозитория на старте. Сетевые измерения не заменяются демонстрационными данными: неготовый механизм помечается как нереализованный, а не как успешный тест.

## Компоненты

| Крейт | Роль | Состояние |
|---|---|---|
| `probe-common` | Схема JSONL, коды ошибок, TOML, ротация журнала | Есть |
| `probe-client` | Пробы и CLI `astp-probe` | Пробы и `test`/`status` есть. `run` и `report` ещё нет |
| `probe-server` | TCP/TLS/HTTP/2 на одном порту, QUIC/HTTP/3 на UDP | Есть |

## Библиотеки

Свой TLS и свой QUIC не пишем.

| Задача | Библиотека |
|---|---|
| Асинхронный ввод-вывод | tokio |
| TLS 1.3 | rustls 0.23, кольцо ring, tokio-rustls |
| HTTP/1.1 и HTTP/2 | hyper 1 |
| QUIC | quinn 0.11 (`rustls-ring`) |
| HTTP/3 | h3 `=0.0.8`, h3-quinn `=0.0.10`, h3-datagram `=0.0.2` |

HTTP/3 на localhost проверяется тестами `astp-transport`, не фактом строки в `Cargo.toml`. Пины с `=` и причина — в `crates/astp-transport/README.md`. `h3-datagram` включает у `h3` feature `i-implement-a-third-party-backend-and-opt-into-breaking-changes`; feature унифицируется на весь workspace.

## Транспорт QUIC (`astp-transport`)

Слушатель — `QuicServer::bind`. Клиент — `quic::connect(ClientTls, SocketAddr, QuicLimits)`. Имя сервера берётся только из `ClientTls`, отдельного SNI у транспорта нет. `rustls::ClientConfig::dangerous` запрещён `clippy.toml`.

Таймауты и лимиты по умолчанию:

| Параметр | Значение |
|---|---|
| `handshake_timeout` | 10 с на путь `Incoming` → `Connecting` → `Connection` |
| `max_pending_handshakes` | 256, сверх лимита `incoming.refuse()` |
| `retry_threshold` | 128: неподтверждённый адрес получает `incoming.retry()` |
| `max_idle_timeout` | 30 с |
| keep-alive клиента | 10 с |
| `max_connections` | 1024 |
| `frame_read_timeout` | 10 с на чтение одного кадра |
| `max_field_section_size` | 16 КиБ |
| буферы datagram | 8 МиБ на приём и на передачу |

0-RTT не включается: `max_early_data_size != 0` или `send_half_rtt_data` — ошибка конфигурации, а не тихая правка. После handshake ALPN `h3` передаётся в HTTP/3. Любое другое значение, включая `h2`, закрывает соединение кодом приложения 0 и пустой причиной (в брифе: `H3_NO_ERROR / 0`; по RFC 9114 число `H3_NO_ERROR` — `0x100`, в коде оставлен ноль из брифа). Привязка к каналу считается сразу после handshake тем же exporter, что в задаче 3.

`POST /t` — тестовый туннель (решение A1): потоковое тело кадров ASTP-M через `FrameReader` и HTTP datagram, привязанные к потоку запроса через quarter stream id. Остальные запросы получают пустой 404. Ошибка `FrameReader` или таймаут чтения кадра закрывает соединение. Это же ограничивает удержание буфера читателя (до 64 КиБ после 4 КиБ + 8 байт от пира).

`h3-datagram` 0.0.2 кодирует quarter stream id в буфер и затем буфер теряет. Для stream id 0 байт заголовка и так нулевой, поэтому один `POST` на соединение привязан верно. Grease выключен, чтобы этот запрос оставался id 0.

## Datagram или поток

Замер — `crates/astp-transport/tests/datagram_vs_stream.rs`. Облегчённый прогон (1000 кадров, 0 % и 3 %) идёт в CI. Полный стенд брифа (10 000 кадров, 2000 кадров/с, 0/1/3 %, payload 64, 512 и 1200) запускается с `--ignored`. JSONL: `docs/measurements/task-04-datagram-vs-stream.jsonl` и `docs/measurements/task-04-datagram-vs-stream-full.jsonl`. Прокси выбрасывает пакеты в обе стороны, сид `0x415354504d310004`, доля `index % 100 < loss`.

Полный стенд, loopback, `conn.max_datagram_size() = 1414`. Дубликатов и порчи байтов нет. `stream_id` запроса — 0. Кадр с payload 1200 (заголовок 8 байт + 1 байт quarter stream id = 1209) проходит одним datagram: при 0 % потерь доставлены все 3333 таких кадра. Закрытие тела запроса прекращает приём datagram этого потока.

| Режим | Потери | Доставлено | p50, мкс | p99, мкс | max, мкс |
|---|---:|---:|---:|---:|---:|
| D | 0 % | 10000 / 10000 | 378 | 809 | 2610 |
| S | 0 % | 10000 / 10000 | 525 | 1202 | 4145 |
| D | 1 % | 9791 / 10000 (97,91 %) | 418 | 5123 | 26317 |
| S | 1 % | 10000 / 10000 | 606 | 15565 | 27417 |
| D | 3 % | 9375 / 10000 (93,75 %) | 441 | 44753 | 78813 |
| S | 3 % | 10000 / 10000 | 534 | 25305 | 32576 |

Правило выбора:

1. Сборка на 1.89 `--locked` без форка и без `[patch]` — да.
2. При 0 % потерь доставлено 100 %, байты совпадают, datagram привязан к stream id 0 — да.
3. При 1 % и 3 % доставка не ниже `(100 − потери − 0,5) %` и p99 D как минимум вдвое ниже p99 S при 3 % — нет. Пороги 98,5 % и 96,5 %, факт 97,91 % и 93,75 %. При 1 % p99 D ниже p99 S в 3,0 раза (5123 против 15565). При 3 % p99 D выше p99 S (44753 против 25305): хвост datagram длиннее, поток за счёт повторной передачи доставляет всё. Прокси режет обе стороны, поэтому ожидаемая доставка эха около `(1 − p)²`: 98,01 % и 94,09 %. Замер рядом с этой оценкой и не подгонялся.
4. Payload 1200 одним datagram при `max_datagram_size` 1414 — да. Комната под payload кадра: 1414 − 8 − 1 = 1405 байт.
5. Паники нет, тест завершается, закрытие потока прекращает datagram — да.

Не выполнено только условие 3. По правилу брифа основной путь QUIC в v1 — datagram (`QUIC_PRIMARY_DATAGRAMS = true`). Поток остаётся: это путь HTTP/2 в задаче 7. Внутренний MTU туннеля по A3 не выбирается здесь. В задачу 12 уходит `max_datagram_size = 1414` и запас payload 1405 байт на этом loopback (MTU пути 1500). Минимум IPv6 1280 плюс заголовок кадра в этот запас укладывается; решение, требовать ли такой путь от сети, остаётся за задачей 12.

## Порты

TCP/TLS/HTTP/2 делят один TCP-порт, по умолчанию 443. QUIC слушает UDP с тем же номером порта и не мешает TCP. Административный приём телеметрии задуман на отдельном адресе с отдельным токеном. Этот приём ещё не написан, секция `[admin]` в конфигурации уже зарезервирована.

## Идентификация теста

Клиент передаёт `test_id` в заголовке `x-astp-test-id` и в query. Сервер пишет событие с тем же идентификатором, и по нему позже стыкуются две стороны. Голый TCP-accept получает собственный идентификатор: до TLS клиент ещё не может передать свой `test_id` по тому же байтовому потоку, не сломав ClientHello.

## Вне этой версии

Полноценный VPN, TUN, сессия ASTP-M, MASQUE, ротация IP, панель пользователей и обход фильтрации как функция сюда не входят. Транспорт QUIC и HTTP/3 описан выше.

# Ревью репозитория: проблемы и исправления

Дата: 2026-11-10. Состояние: `main` @ `4c62eea`.

Проверено: весь код прочитан, `cargo clippy --workspace --all-targets` чист, `cargo test --workspace` — один тест падает (п. 1.4), остальные проходят. Находки получены чтением кода; эксплуатационные сценарии (исчерпание слотов, флуд) вживую не воспроизводились.

Архитектурная вводная, учтённая в ревью: ASTP-M — асинхронный каскад. Аплоад клиента уходит на один сервер, даунлоад приходит с другого. Спецификацию split-path я не видел, поэтому раздел 2 опирается только на то, что есть в коде, и местами это вопросы к спецификации, а не готовые решения.

Приоритеты: **P1** — исправить до эксплуатации, **P2** — исправить в ближайших задачах, **P3** — мелочи.

## 1. Исправить в первую очередь

### 1.1. P1 — простаивающие соединения держат слот до часа

**Где:** `crates/probe-server/src/lib.rs:242-251`.

**Проблема.** Таймер задан только для HTTP/2 (`builder.http2().timer(...)`). У HTTP/1.1 таймера нет, и hyper молча не применяет таймаут чтения заголовков (`hyper/src/common/time.rs`: default-таймаут без таймера → `None`). Простой после TLS-рукопожатия сервер не ограничивает вообще: `idle_timeout_seconds` используется только в QUIC и в upload. Соединение живёт до `max_session_seconds + 30`. При лимите 32 из примера конфига 32 молчащих клиента блокируют пробник на час.

**Как исправить.**

- Задать таймер и для HTTP/1: `builder.http1().timer(TokioTimer::new()).header_read_timeout(...)`.
- Ввести таймаут простоя на уровне соединения: обёртка над `Counting<TcpStream>`, которая рвёт соединение, если счётчики байт не менялись `idle_timeout_seconds`.
- **Каскад:** простой считать по сумме направлений или по «своему» направлению, но не требовать трафика в обе стороны. На аплоад-сервере соединение легитимно почти ничего не отдаёт, на даунлоад-сервере — почти ничего не принимает. Таймаут вида «нет входящих N секунд» убьёт нормальное даунлоад-соединение.
- Тест: соединение после рукопожатия молчит → слот освобождается через `idle_timeout_seconds`.

### 1.2. P1 — systemd-юниты запускают процесс от root

**Где:** `deploy/systemd/astp-probe-server.service`, `astp-probe-client.service`.

**Проблема.** Нет `User=`/`DynamicUser=`. `ReadWritePaths=/var/lib/astp-probe` уронит юнит с `226/NAMESPACE`, если каталога нет.

**Как исправить.**

```ini
DynamicUser=yes
StateDirectory=astp-probe
AmbientCapabilities=CAP_NET_BIND_SERVICE
CapabilityBoundingSet=CAP_NET_BIND_SERVICE
```

`ReadWritePaths` после этого убрать. Ключ TLS сделать читаемым через `LoadCredential=` или группу. Клиенту с `bind_interface` дополнительно нужен `CAP_NET_RAW` (SO_BINDTODEVICE).

### 1.3. P1 — клиентский юнит уходит в бесконечный рестарт

**Где:** `deploy/systemd/astp-probe-client.service`, `crates/probe-client/src/main.rs:118`.

**Проблема.** `astp-probe run` сразу выходит с кодом 1. `Restart=on-failure` + `RestartSec=3` дают 5 запусков за 12+ секунд и не упираются в стандартный `StartLimitBurst=5`/10 с.

**Как исправить.** До реализации `run` — выходить особым кодом и добавить `RestartPreventExitStatus=<код>`, либо не поставлять юнит. Дополнительно `StartLimitIntervalSec=60`, `StartLimitBurst=5`.

### 1.4. P1 — тест `timeout_is_classified` зависит от сети

**Где:** `crates/probe-client/src/netutil.rs:145-162`.

**Проблема.** Тест стучится в `192.0.2.1:9` и принимает только `TcpTimeout` или `LocalNetworkUnavailable`. В окружении с прокси/фильтром приходит `TcpRefused` — тест падает (так было при этом ревью). Тот же класс, что уже чинили в `dns_failure_is_classified`.

**Как исправить.** Сделать тест герметичным: локальный listener с `backlog = 1`, забитый соединениями, чтобы SYN остался без ответа; либо проверять классификацию через `ErrorCode::from_connect_error` на синтетической ошибке (уже покрыто) и убрать сетевой тест.

### 1.5. P1 — пример конфига клиента не соответствует схеме

**Где:** `configs/client.example.toml:27-31`, `crates/probe-common/src/config.rs:125-133`.

**Проблема.** В закомментированной `[delivery]` есть `ca_file` и `tls_server_name`. `DeliverySection` принимает только `url` и `token_env` при `deny_unknown_fields`. Раскомментировал — конфиг не парсится.

**Как исправить.** Добавить оба поля в `DeliverySection` (они понадобятся) или убрать из примера. Добавить тест, который парсит пример с раскомментированными секциями.

### 1.6. P2 — оборванная по дедлайну загрузка пишется как успех

**Где:** `crates/probe-server/src/body.rs:82-85`.

**Проблема.** `completed = true` ставится и при `remaining == 0`, и при истечении дедлайна. Событие `download` получает `success` и `phase=completed`, хотя `Content-Length` не выдан.

**Как исправить.** Развести причины: для download считать успехом только `remaining == 0`; дедлайн → `fail(ApplicationTimeout, ...)`. Для session дедлайн — нормальное завершение, а исчерпание `max_session_bytes` раньше срока — отдельная пометка в `detail`.

### 1.7. P3 — `bytes_sent` для `/probe` завышен на 1

**Где:** `crates/probe-server/src/handler.rs:237`.

**Проблема.** Пишется 9, а `"ok astp\n"` — 8 байт. Ветка HTTP/3 считает через `body.len()` верно.

**Как исправить.** Вынести тела ответов в константы и логировать `BODY.len()` в обеих ветках.

## 2. Что следует из асинхронного каскада

Сейчас и пробник, и каркас ASTP-M молча предполагают один сервер и одно двунаправленное соединение. README прямо говорит: «Параллельный каскад (два сервера) в v1 не входит», а коды `0x40..=0x4F` и TLV `0x000C`/`0x000D` только зарезервированы под split-path.

### 2.1. P1 — README противоречит архитектуре

**Где:** `README.md:15`, `docs/architecture.md` («Вне этой версии»).

**Как исправить.** Зафиксировать решение явно: либо каскад входит в v1 и документы правятся, либо v1 остаётся односерверным, а каскад — следующая версия. От этого зависят пункты ниже.

### 2.2. P1 — пробник не измеряет то, что нужно каскаду

**Проблема.** Каждая проба ходит на одну цель и проверяет оба направления одного соединения. Для каскада важны две независимые величины: аплоад до сервера A и даунлоад от сервера B. Сейчас:

- у цели нет роли (`TargetConfig` не различает аплоад- и даунлоад-узел);
- длинная сессия у клиента только на приём (`stream::long_session` → `GET /session`). Серверный `POST /session` (`handler.rs:157-222`, `direction=up`) клиентом не вызывается вообще;
- нет теста «аплоад на A и даунлоад с B одновременно» — а именно так будет выглядеть рабочая нагрузка. `run_long` идёт по целям строго по очереди;
- `test_id` у проб к A и к B разный, связать пару событий нечем.

**Как исправить.**

- Добавить в `TargetConfig` поле роли (`role = "uplink" | "downlink" | "both"`, по умолчанию `both`) и запускать только пробы своего направления.
- Реализовать клиентскую upload-сессию к `POST /session` с тем же детектором зависаний, что у download.
- Добавить парную пробу: одновременно upload на A и download с B, общий `pair_id` в событиях обеих сторон.
- В схему событий добавить `direction` полем, а не строкой в `detail`.
- `docs/measurement-methodology.md`: правило «пробы идут по очереди» дополнить исключением для парной пробы.

### 2.3. P2 — метки времени для сведения журналов двух серверов

**Где:** `crates/probe-common/src/timefmt.rs:9-20`.

**Проблема.** Метка времени обрезается до секунд. Для стыковки событий клиента, сервера A и сервера B этого мало, а расхождение часов между серверами не оценивается никак.

**Как исправить.** Писать миллисекунды (это изменение схемы — поднять `SCHEMA_VERSION` или читать оба формата). В событие сервера добавить длительность по монотонным часам от начала соединения. В методику — требование NTP/chrony на обоих серверах и оценку смещения.

### 2.4. P1 — привязка аутентификации к каналу при двух соединениях

**Где:** `crates/astp-crypto/src/auth.rs` (`channel_binding`, `Authenticator`), `crates/astp-frame/src/config.rs:67` (`SessionId` — «Not a secret»).

**Проблема.** Привязка — TLS-экспортер одного соединения. В каскаде соединений два, к разным серверам, и экспортеры у них разные. Контракт `Authenticator::verify(binding, credential)` не отвечает на вопрос, как сервер B убеждается, что его даунлоад-соединение принадлежит той же сессии, что аплоад-соединение на A. Если склейка пойдёт по `session_id`, который объявлен несекретным, чужой даунлоад можно будет перехватить, зная идентификатор.

**Как исправить (на уровне спецификации).**

- Клиент аутентифицируется на каждом сервере отдельно, credential привязан к экспортеру своего соединения.
- Склейка двух половин — по секретному значению, выведенному из общего секрета сессии и обоих экспортеров, а не по `session_id`.
- Определить, как A и B обмениваются состоянием сессии и что происходит, когда одна половина упала.
- В `Authenticator` добавить роль соединения (uplink/downlink), чтобы credential одного направления нельзя было предъявить на другом.

### 2.5. P2 — кадры, которые предполагают ответ по тому же соединению

**Где:** `crates/astp-frame/src/types.rs` (`Ping`/`Pong`, `Window`, `ConfigAck`), `crates/astp-types/src/lib.rs`.

**Проблема.** Кодек нейтрален к направлению, но семантика кадров — нет:

- `PING` → `PONG` «с теми же 8 байтами»: в каскаде `PONG` придёт по другому соединению от другого сервера. RTT получится суммой двух путей, а «жив ли этот путь» по нему не определить;
- `WINDOW` (кредит): получатель данных и отправитель кредита находятся на разных путях;
- `CONFIG` → `CONFIG_ACK` и `KEY_EPOCH`: не определено, по какому пути идёт подтверждение и как согласуется эпоха между двумя соединениями;
- `Keepalive`/`IdleTimeout` TLV — одно значение на сессию, хотя пути разные.

**Как исправить.** В спецификации для каждого управляющего кадра указать путь ответа. Проще всего — оставить на каждом соединении тонкий обратный канал для `PONG`/`WINDOW`/`CONFIG_ACK`: тогда существующие кадры работают без изменений, а однонаправленным остаётся только трафик TUN. Если обратного канала нет — занять зарезервированные `0x40..=0x4F` под кадры с идентификатором пути. Изменений в самом `astp-frame` это пока не требует.

### 2.6. P2 — однонаправленный трафик как признак для анализа

**Проблема.** Маскировка (`camouflage_pad_len`, ALPN `h3`/`h2`) рассчитана на размер отдельных кадров. В каскаде на проводе появляется HTTPS-соединение, которое только отдаёт, и второе, которое только принимает. Долгий аплоад без сопоставимого ответа нетипичен для обычного сайта, и паддинг кадров это не скрывает.

**Как исправить.** Заложить в профиль маскировки покрывающий трафик в обратном направлении (кадры `PADDING` уже есть) и зафиксировать допустимое соотношение направлений. Это же даёт обратный канал из п. 2.5.
